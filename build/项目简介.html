企业外置知识库

KB Hub · 独立部署的企业知识中枢
项目简介

一、这是什么

企业外置知识库是一套可以独立部署、供多个企业项目同时接入的知识服务。它把散落在各部门的文档、制度、手册、FAQ 收拢到一个统一的检索层，再以两种方式对外提供能力：一种是标准 REST API，供企业业务系统直接调用；另一种是 MCP 插件，供 AI Agent 挂载使用。

它不是某个业务系统的附属模块，而是一个横向的基础设施——任何需要"查内部资料"的系统都能接进来，而不必各自维护一份文档索引。

一句话定位：企业内部的资料，存得全、检得准、答得快，并且不同企业、不同职级看到的范围严格不同。

二、解决的三个问题

企业员工上传内部资料，真正的难点不在"上传"，而在上传之后的三个环节。这三件事各自需要独立的设计，任何一环缺失都会让整个知识库失去价值。

问题常见做法及其后果本项目的做法
怎么完整保存 先解析文字，解析成功才存文件。扫描件、加密 PDF、损坏文件解析必然失败，原件就此丢失，事后无法追溯。 先落盘、再解析。原件按内容哈希永久保存，解析失败也照样入库并标记状态，员工仍可下载原文。每次内容变更另存一个版本，旧版不覆盖。
怎么准确检索 只用关键词匹配，词对得上就返回。问题是"词对得上但不是这一段"，排序靠猜。 词法加权的混合检索。在 BM25 之上叠加短语命中、章节标题命中、命中词邻近度、数字硬词四项加权；再融合一路向量召回补语义。每一项得分都可通过参数单独查看。
怎么快速回答 把检索到的片段直接丢给大模型，模型在没有依据时自行编造，答案看起来合理但无法核对。 FAQ 前置 + 缓存 + 带引用作答。高频问题直接命中标准答案；配置大模型后输出生成式答案，未配置时输出原文摘录并明确标注。知识库无依据时返回空结果，而不是编一个。

三、三个关键设计

1. 一个企业一套服务、一个数据库文件

不是在同一张表里加一列租户标识，也不是一套服务托管多家企业，而是每个企业单独部署一套服务，指向自己的数据库文件：业务数据、后台账号、API 密钥、向量索引全部在这一个 .db 里，原始文件放在旁边的 files/ 目录。企业之间连数据库连接都不共享，不存在「某个查询漏写了条件」导致数据串家的可能。备份是拷一个文件，迁移是改一条路径，下线是删一个目录。

2. 角色与职级两个维度共同决定权限

企业内常见的现实是：一个人能做什么操作（上传、删除、管人）和能看到什么内容（公开、内部、机密）是两件事。只用一个"管理员 / 普通用户"划分，要么管不住机密文件，要么把普通员工挡在门外。本项目把二者拆开：五个角色决定操作权限，五个员工等级决定数据可见范围，二者交叉生效。文档本身带密级，检索时在数据库层面就过滤掉越级内容——不是查到了再隐藏。

3. 每个企业有独立的管理后台

企业管理员登录自己的后台，可以管理本企业的成员账号、分配角色与等级、签发 API 密钥、调整文档密级、查看操作审计。后台的权限同样受角色与等级双重约束，并且内置防提权规则：不能被授予比自己更高的角色，不能管理等级高于自己的成员，任何时刻必须保留至少一位企业负责人。

服务本身零外部依赖：不需要安装任何 npm 包，不需要单独的数据库服务器，Node.js 22 自带的 SQLite 就是存储引擎。整个系统解压即可运行，这对内网部署和审计合规是决定性的优势。
