1　项目概述

1.1 项目定位

企业外置知识库（下称"知识库"）是一套可独立部署的知识服务，供多个企业项目同时接入。它把企业内部分散的文档、制度、手册、问答对收拢为统一的检索层，并以两种标准化方式对外提供能力：

  • REST API：企业业务系统、内部工具直接调用，无需了解内部实现。
  • MCP 插件：以 Model Context Protocol 标准接入 AI Agent，Agent 可以直接"查资料"。

两条通道共用同一套服务端逻辑，因此同一个问题通过 REST 和通过 AI Agent 得到的检索结果完全一致，不存在两套索引各自为政的问题。

1.2 项目起源与要解决的问题

项目的出发点是三个具体的业务诉求：企业员工上传内部资料之后，如何完整保存、如何准确检索、如何快速回答。这三个诉求对应三套独立机制，缺一不可。

诉求失败模式对应机制
完整保存 先解析再决定存不存，解析失败即丢失原件；文档改版后覆盖旧版，无法追溯历史。 原始件先落盘、按内容哈希去重、解析失败仍入库并标记状态、每次变更写版本记录。
准确检索 纯关键词匹配，词对上但语义不对；长文档切块过粗，命中段落包含无关内容。 BM25 叠加四项语义加权，融合向量召回；按标题层级切块，命中后向相邻块扩展上下文。
快速回答 直接让大模型读片段作答，无依据时编造；每次提问都重新走完整链路。 FAQ 前置直答、结果缓存、抽取式与生成式双模式、答案带编号引用；无依据时明确返回空。

1.3 设计原则

原则含义与取舍
零外部依赖 不需要 npm install，不需要独立数据库服务，使用 Node.js 22 内置 SQLite。内网、离线、审计受限环境下可直接部署。
物理隔离优先 一个企业一套服务、一个数据库文件。企业之间靠部署边界与文件系统隔离，连数据库连接都不共享，不存在「漏写条件」的可能。
宁可少答，不可错答 知识库没有依据时返回空结果并由调用方转人工，而不是让模型补一个看起来合理的答案。
结果可解释 检索每一分项都可单独查看，密级过滤在前端可验证，向量通道可单独关闭对比。出问题能定位，而不是"就是不准"。
不重复造轮子 文档切分、检索、向量化都在服务端完成，前端与 Agent 侧只做展示，避免多端逻辑漂移。

3　单实例部署与数据文件

本项目不做「一套服务托管多个企业」。一个企业部署一套服务，服务只认自己那一个数据库文件；两个企业之间连数据库连接都不共享。

3.1 部署形态

企业 A 的服务器                        企业 B 的服务器
┌──────────────────────────┐         ┌──────────────────────────┐
│ kb-hub 进程（端口 7300）  │         │ kb-hub 进程（端口 7300）  │
│  config.json             │         │  config.json             │
│   ├ instance.id = acme   │         │   ├ instance.id = beta   │
│   └ database = …/kb.db   │         │   └ database = …/kb.db   │
└────────────┬─────────────┘         └────────────┬─────────────┘
             │                                     │
      data/kb.db + data/files/              data/kb.db + data/files/
   账号、文档、向量全在这一个文件里      与 A 完全无关，互不可见

隔离不是靠 SQL 里的 WHERE tenant_id = ?，而是靠「压根连不到对方的库」。这样即使业务代码写错条件，也不可能读到另一家企业的数据。

3.2 数据目录与配置

一个企业需要维护的只有两样东西：一个 .db 文件和一个 files/ 目录。

data/                         可用 config.dataDir 改根目录
├── kb.db                     唯一数据库（业务表 + 账号 + 密钥 + 审计 + 向量）
└── files/
    ├── 04/04a1…f3.docx       原始件按 sha256 前两位分桶，内容相同的只存一份
    └── a6/a6c9…21.pdf

数据库位置在 config.json 里指定，也可以用环境变量覆盖，适合把数据放到独立磁盘或加密卷：

{
  "instance": { "id": "acme", "name": "示例科技有限公司" },
  "dataDir": "data",
  "database": "data/kb.db"
}

# 或临时指定（优先级最高）
KB_DB=/mnt/secure/acme/kb.db node server.js

首次启动会自动建库、建表、建默认空间，不需要手动执行 SQL。已有旧数据时会在启动阶段自动迁移（见 3.5）。

3.3 为什么放弃「一套服务管多企业」

早期版本确实是多租户：一个控制库存租户注册表，每个企业一个子库。实际用下来，多出来的复杂度并不值得——尤其是运维和故障隔离这两块。

维度一套服务管多企业（旧）一企一部署（现在）
隔离强度靠代码里每处查询都写对租户条件，漏一处就是跨企业泄漏靠进程与文件边界，写错也读不到别人的库
故障面一个企业的坏数据、慢查询、库损坏会拖累所有人互不影响，单个企业可以随时重启、回滚、换机器
备份与迁移要么整库备份，要么按租户导出，导出逻辑本身要维护拷一个文件 + 一个目录，换台机器改条路径就能跑
升级一次升级影响全部企业，必须同时兼容所有租户的数据版本逐家升级，出问题只影响一家，可灰度
配额与计费要在库里做配额表、限流表交给部署层（容器配额、磁盘配额、网关限流）
代价—每家要跑一个进程；跨企业汇总要另做运维层，不能靠一条 SQL

如果将来确实需要「一个控制台看所有企业」，正确做法是在外层做一个运维平台，把各实例的 GET /v1/admin/instance 汇总起来，而不是把数据重新塞回一个库。

3.4 数据库里有什么

单库共 16 张表，按职责分四组。所有表都保留 tenant_id 列，值固定等于 config.instance.id——这样历史 SQL 不用重写，也多一层显式标记。

分组表职责
身份与接入instance本企业信息，永远只有一行
api_keys接入密钥，只存哈希；带 reader_level 限定可读密级
admin_users后台账号：角色 + 员工等级双维度
admin_sessions后台会话，可随时吊销
audit_logs操作审计：谁、什么时候、对什么、结果如何
知识内容spaces知识空间（部门 / 主题分区）
documents文档元数据：来源、哈希、密级、解析状态、版本
chunks切块后的正文，带章节路径
terms倒排索引：词 → 块 → 词频
corpus_stats语料统计，供 BM25 计算
faqs标准问答，命中时优先于文档检索
doc_files原始件元数据，内容按 sha256 去重
document_versions版本历史，旧版原始件保留
sync_cursors增量同步游标
向量vectors每块一条，Float32 BLOB；与原文同库，少一个文件要备份
vec_meta向量模型与维度，用于判断是否需要重建

3.5 从旧的多租户版本升级

旧版本的目录是 data/tenants/<企业ID>/。新版本首次启动时会自动迁移，规则如下：

  1. 选主企业：优先读 config.instance.legacyTenant；没配就取旧控制库里最早创建的租户；再没有就取文档最多的目录。
  2. 清空单库业务表，从该企业目录导入文档、块、倒排、FAQ、原件元数据与向量。
  3. 把账号、密钥、会话、审计里的租户标记统一改成 config.instance.id。
  4. 其他旧租户的记录从单库移除（原始目录 data/tenants/ 不会被删，随时可查）。

迁移日志会打印在启动输出里，例如：

[db] 已从旧目录 t_demo 重建单库：10 篇文档 → /opt/kb/data/kb.db
[db] 单实例化：已从库中移除其他旧租户的 22 条业务记录（原始目录 data/tenants/ 未删除）

迁移前建议先整目录备份一次。确认新库正常后，data/tenants/ 可以整体删除。

3.6 备份、迁移与克隆

# 备份（无需停服）
复制 data/kb.db（连同 -wal / -shm）与 data/files/ 整个目录

# 迁移到另一台机器
停服 → 复制 data/ → 新机器改 config.json 的 database 指向它 → 启动

# 克隆一套测试环境
复制 data/ 到别处 → 用 KB_DB 指向副本启动，正式库不受影响

SQLite 处于 WAL 模式。热备份时要么一并复制 -wal 与 -shm，要么先执行 PRAGMA wal_checkpoint(TRUNCATE)。

4　权限模型

4.1 两个正交维度

企业里的权限实际上是两件不同的事，必须拆开建模：

  • 能做什么操作——能否上传、能否删除、能否管人、能否签发密钥。由角色决定。
  • 能看到什么内容——公开资料、内部制度、部门数据、管理层文件、机密方案。由员工职级决定。

只用一个维度会导致两种极端：按角色划分则"内容编辑"能看全部机密；按职级划分则"部门主管"无法管理文档。两个维度交叉后，一个"部门主管 + L3"自然获得"能管文档、能看部门级且看不到机密"的合理组合。

4.2 角色定义

角色名称权限范围
owner企业负责人全部权限，含成员管理、密钥签发与安全设置。每个企业必须至少保留一位。
admin知识库管理员管理文档、空间、FAQ、密钥与成员；不能改动企业负责人。
manager部门主管管理文档与密级、可查看审计、可邀请成员；不能签发密钥。
editor内容编辑上传与维护文档、维护 FAQ、查看统计；不能删除成员或签发密钥。
viewer只读成员只能检索、查看文档与统计。

4.4 职级定义

职级对应岗位可读文档密级典型场景
L1普通员工公开新员工入职查询制度、报销标准、IT 支持流程
L2高级员工 / 组长公开 + 内部查阅部门内部规范、项目流程
L3主管至部门级查阅部门预算口径、团队管理资料
L4经理 / 总监至管理层查阅报价体系、折扣审批权限
L5高管 / 企业负责人全部（含机密）查阅薪酬方案、期权计划

文档侧同样有五档密级：公开、内部、部门、管理、机密，与职级一一对应。一份文档设成"管理"级，则只有 L4 及以上人员可检索到。

4.5 密钥的数据等级

企业系统对接通常不区分"人"，而是一个服务账号代表某种用途。因此 API 密钥也带一个可读等级上限，默认 L5（即与企业数据权限一致）。给客服机器人签发 L1 密钥，它就只能检索公开资料——即使它的密钥泄露，也拿不到机密文档。

请求侧还可以进一步压低：请求体传 level，实际生效等级取密钥等级与该值中的较小者。这意味着调用方永远无法通过参数抬高自己的权限，只能自我限制。响应中会回显本次实际生效的等级，便于排查"为什么查不到"。

实际生效等级 = min(密钥的 reader_level, 请求体中的 level)

4.6 防提权规则

后台的成员管理内置以下约束，任何一条不满足都会被拒绝：

  1. 只有企业负责人（owner）能授予 owner 角色。
  2. 不能管理与自己同级或更高级的角色。
  3. 不能修改职级高于自己的成员。
  4. 不能删除自己。
  5. 企业内任何时刻必须保留至少一位 owner。

4.7 密级过滤必须处处生效

这是一个容易出错的点：密级过滤不能只在检索接口上做。只要有一个入口没过滤，低职级人员就能绕道拿到机密内容。本项目在以下入口全部实施过滤，并有对应的自动化断言：

入口过滤行为
检索 /v1/search越级切块在候选阶段即被排除，不参与打分
问答 /v1/ask检索结果与 FAQ 命中均按等级过滤
文档列表 /v1/documents按等级过滤，支持 level 参数进一步压低
文档详情 /v1/documents/:id越级文档统一返回 404，不暴露存在性
原件下载 /v1/documents/:id/file越级返回 403（文档可见但原件受保护）
FAQ 列表 /v1/faqs按等级过滤，与问答接口口径一致
企业概览 /v1/meta文档数、块数、问答数按等级统计，另给总数表示规模
管理后台成员只见自己等级内的文档；owner 可见全部
MCP 插件透传 level，输出标注密级并提示不要臆测更高密级内容

4.8 会话与密码

项目实现

5　资料入库

5.1 入库顺序：先落盘，再解析

这个顺序是关键。如果先解析、解析成功才保存文件，那么扫描件、加密 PDF、损坏文件一旦解析失败，原件就永久丢失了——而这恰恰是最需要人工查看的文件。

接收文件
   ↓
计算 sha256 → 落盘到 files/<前两位>/<sha256>.<ext>   ← 无论后续如何，原件已安全
   ↓
解析抽取文字
   ├─ 成功 → 切块 → 建倒排 → 写向量 → 状态 ok
   └─ 失败 → 建空索引 → 状态 failed，记录原因   ← 仍可下载、可追溯
   ↓
写版本记录（内容有变更时）

解析失败的文件会出现在企业概览的"解析失败"计数中，运营可据此补做 OCR 或要求上传可复制文本的版本。

5.2 幂等与版本

入库以 source_uri（来源标识）加内容哈希作为幂等键。同一来源、内容未变时直接返回"跳过"，不重建索引；内容变化时自动升版本、重建索引，并保留旧版原件。

注意：幂等键包含来源标识。同一个文件分别以种子数据、命令行路径、网页上传三种来源入库，会被视为三份不同来源而各存一份。这是设计如此——用于区分"同一份文件的不同获取渠道"，但在批量导入时应固定使用同一种入口，避免重复。

还有一种常见需求是"内容没变，只想调整密级"。此时若在入库时显式传入新的密级，系统会更新密级并返回"跳过 + 已调整密级"的标记，不必重新解析。

5.3 切块策略

参数默认值说明
块最大字符数700条款类文档可调小至 400 提高精度，叙事类可调大至 1000 保留上下文
相邻块重叠80 字符按句子边界重叠，避免答案被切在块边界处截断
切分依据标题层级按 Markdown 标题、Word 标题样式分层，块的章节路径一并保存
纯标题块丢弃只有标题没有正文的块不参与检索，避免"标题命中但内容为空"

检索按小块算分（精度高），命中后自动补齐同一章节的前后相邻块（最多 1400 字），因此调用方拿到的是完整段落而不是半句话。

6　检索与问答

6.1 混合检索的两路

企业内网环境有两类查询并存：一类是术语精确匹配（系统名、错误码、产品代号、金额数字），另一类是口语化提问（"住一晚酒店最多能报多少钱"）。前者词法检索更强，后者需要语义理解。因此采用两路融合：

最终得分 = 0.7 × (词法分 / 本次最高词法分) + 0.3 × 向量余弦

两路权重均可配置。向量通道在两种情况下自动关闭：该企业尚未建立向量库，或请求显式传 vector:false。关闭后退化为纯词法检索，此时词法权重为 1。

6.2 词法分的四项加权

基础分是 BM25，但它只能回答"词出现了几次"。真正的难点是"词对得上但不是这一段"，因此在其上叠加四项调整：

加权项系数解决的问题
短语命中×1.35整句原文出现在段落中，是最强的相关性信号
章节标题命中×1.20"住宿标准"这类问题应落在同名小节，而非正文其他地方
文档标题命中×1.15提问指向某份制度时，该制度的块应优先
命中词邻近度×1.12查询词散落在文首和文尾，大概率不是同一件事
数字 / 英文硬词×0.75~1.20问"600 元"时，命中"400 元"的段落必须被压低

每个分项都可以通过请求参数 debug:true 单独查看，便于定位"为什么这条排第一"。

6.3 向量通道

项目说明
存储位置本企业数据库里的 vectors 表（与原文同库），字段为切块 ID、文档 ID、空间 ID、维度、模型名、向量二进制、更新时间
默认模型本地确定性哈希向量，256 维，不联网、无成本
远程模型配置 OpenAI 兼容接口后自动切换，支持任意维度
模型隔离模型名与维度随向量一起记录，切换模型后旧向量自动失效并提示重建
检索方式内存全量点积，企业级数据量下耗时可忽略

6.4 两种防止噪声的设计

融合两路分数时，最容易被忽略的问题是：向量余弦对任何两个文本都会给出一个非零值，哪怕它们毫不相关。这会让"什么都不像"的切块也获得一定分数，稀释真正的结果。因此加了两道闸：

  1. 余弦噪声门限：余弦低于 0.25 时按 0 计算，不参与融合。
  2. 语义救援：仅当某个切块词法分为 0、但余弦不低于 0.45 时，才允许它进入结果，且最多 2 条。用于处理"完全换了说法"的提问。

这两道闸是实测调出来的：不加时，混合检索的排序质量会明显低于纯词法；加上后与词法加权持平，同时保留了向量通道在换词提问上的价值。

6.5 问答编排

提问
 ↓
FAQ 精确命中？ ──是──→ 直接返回标准答案（约 0 毫秒）
 ↓否
结果缓存命中？ ──是──→ 直接返回（0~1 毫秒）
 ↓否
混合检索（5~15 毫秒）
 ↓
配置了大模型？ ──是──→ 生成式答案，带编号引用
              └─否──→ 原文摘录，标注"原文摘录"
 ↓
知识库无依据 → 返回空结果，mode = empty

问答结果带四种模式，调用方据此决定展示方式：

模式含义建议展示方式
faq命中标准问答条目直接展示，可信度最高
llm大模型基于检索结果生成正常展示，保留引用来源
extractive未配大模型，返回原文摘录展示时标注"原文摘录"
empty知识库无相关内容不要让模型自行补答案，转人工或提示补充文档

6.6 缓存策略

检索与问答结果进入容量 2000 条、有效期 2~3 分钟的缓存。关键在于失效方式：任何写操作（入库、删除、重建索引）都会让一个全局版本号递增，旧缓存整体作废，而不是逐个维护依赖关系。这样实现简单，且绝不会返回过期结果。

12.2 检索质量评测

node scripts/eval-retrieval.js 在一份 14 篇文档、28 条人工标注问题的集合上做三模式对比，其中 6 条为"换词题"（与原文几乎没有相同词，只能靠语义通道）。

13　已知限制

限制说明规避方式
扫描件无 OCR图片型 PDF、纯截图幻灯片抽不出文字，标记为解析失败原件已保存不会丢；补做 OCR 后重传，或上传可复制文本的版本
PDF 中文可能乱码内置解析不处理部分中文字体映射安装 pypdf 等外部工具后可改善；解析失败计数会暴露这类文件
不支持旧版二进制格式.doc / .ppt / .xls 无法解析另存为 .docx / .pptx / .xlsx
本地向量不具语义能力哈希向量只做词形近似，不做同义改写配置真实 embedding 接口后自动改善
单机单进程写SQLite 写锁，并发写会等待入库任务串行化，单文档控制在 5 万字符内
原件不做容量治理删除文档后原件仍占磁盘按引用关系定期清理孤儿文件
无单点登录后台仅支持邮箱密码接入企业 SSO 时替换登录认证段即可
同义词表需人工维护不会自动学习从审计日志的零结果查询中提炼补充
