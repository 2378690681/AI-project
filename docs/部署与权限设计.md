# 部署形态、权限与向量库

这一版把「一套服务托管多个企业」改成了 **一个企业一套服务、一个数据库文件**。
下面写清部署边界、迁移规则、权限判定和向量实现，以及为什么这么选。

---

## 1. 部署形态

### 1.1 一个企业 = 一个进程 + 一个库 + 一个原件目录

```
/opt/kb-acme/                     企业 A 的一套部署（独立进程、独立端口）
├── config.json                   instance.id = acme
├── data/
│   ├── kb.db                     全部业务数据：文档、块、词条、FAQ、向量、密钥、账号、审计
│   └── files/<aa>/<sha>.<ext>    原始件（按内容哈希去重）
└── server.js

/opt/kb-globex/                   企业 B 的另一套部署，与 A 没有任何共享
├── config.json                   instance.id = globex
└── data/kb.db
```

企业之间的隔离**不靠 SQL 条件**，靠的是：不同进程、不同数据库文件、不同文件系统目录。
一个进程只打开自己的 `kb.db`，代码里没有任何一条查询能读到别家的数据 —— 因为别家的数据根本不在这个文件里。

### 1.2 数据库里有什么（16 张表）

| 分组 | 表 | 说明 |
|---|---|---|
| 实例 | `instance` | 永远只有一行，`id` = `config.instance.id`（默认 `default`） |
| 身份 | `api_keys`、`admin_users`、`admin_sessions` | 对外密钥、后台账号、会话 |
| 知识 | `spaces`、`documents`、`chunks`、`terms`、`corpus_stats` | 空间、文档、检索块、倒排词条、语料统计 |
| 辅助 | `faqs`、`doc_files`、`document_versions`、`sync_cursors` | 问答对、原件元数据、版本历史、同步游标 |
| 向量 | `vectors`、`vec_meta` | 向量与模型元信息，与原文同库 |
| 审计 | `audit_logs` | 调用与操作记录 |

业务表仍保留 `tenant_id` 列，值恒等于 `config.instance.id`。
留着它有两个原因：一是旧代码里几百条 `WHERE tenant_id = ?` 不用重写；二是旧库升级时能把历史数据认领进来。
**它不再承担隔离职责**，只当一个「归属标记」。

### 1.3 为什么放弃「一套服务管多企业」

早期版本确实是多租户：一个控制库存企业注册表，每个企业一个子库、一个独立向量文件。
实际跑下来，多出来的复杂度不值这个价：

| 关注点 | 一套服务管多企业（旧） | 一个企业一套服务（现在） |
|---|---|---|
| 隔离正确性 | 每处查询都得写对条件，漏一处就是跨企业泄漏 | 隔离由部署边界完成，写错也读不到别家 |
| 备份单个企业 | 要么整库备份，要么按企业导出，导出逻辑自己维护 | 拷一个 `.db` + 一个 `files/` |
| 单企业故障 | 一个库锁表/损坏，同进程内其他企业一起受影响 | 互不影响，重启也只重启那一套 |
| 升级 | 一次升级影响全部企业，必须同时兼容所有数据版本 | 逐企业灰度，出问题只回滚一家 |
| 计费/配额 | 按行统计，边界模糊 | 按文件大小、按目录，天然清楚 |
| 加新企业 | 调接口注册，改代码风险 | 复制一份目录、改 `instance.id`、换端口 |

代价是「加一个企业要起一套服务」。但企业客户数量是个位数到几十的量级，
这套代价远小于「隔离写漏一次」的代价。

### 1.4 从旧的多租户版本升级

旧版本目录是 `data/tenants/<企业ID>/`。新版本首次启动会自动迁移，规则：

1. **选主企业**：优先读 `config.instance.legacyTenant`；没配就取旧控制库里最早创建的企业；再没有就取文档最多的目录。
2. **清空重建**：把单库里已写入的业务表清空，再从选中的旧目录整体导入（含 `vectors.db` 与 `files/`）。
3. **归一归属**：账号、密钥、会话、审计里的 `tenant_id` 统一改成 `config.instance.id`。
4. **其余移除**：其他旧企业的业务记录从单库移除，**旧目录 `data/tenants/` 保留不删**，随时可查。

启动时会打印：

```
[db] 已从旧目录 t_demo 重建单库：10 篇文档 → /opt/kb-acme/data/kb.db
[db] 单实例化：已从库中移除其他旧企业的 22 条业务记录（原始目录 data/tenants/ 未删除）
```

迁移前建议整目录备份一次。确认新库正常后，`data/tenants/` 可以整体删除。

### 1.5 克隆第二家企业

```bash
# 1) 停掉模板实例，复制目录（不带 data）
mkdir /opt/kb-globex && cp -r /opt/kb-acme/{server.js,src,public,cli.js,mcp} /opt/kb-globex/

# 2) 全新初始化，指定自己的 instance.id
cd /opt/kb-globex
KB_INSTANCE_ID=globex node cli.js init
node cli.js tenant:create "示例科技有限公司" --owner-email ops@globex.com

# 3) 换端口启动
PORT=7301 node server.js
```

也可以用环境变量覆盖：`KB_INSTANCE_ID` / `KB_INSTANCE_NAME` / `KB_DB`（库路径）。
`config.database` 是个 getter，脚本在 import 之后设 `process.env.KB_DB` 也生效 —— 自测就是靠这个跑在临时库上的。

## 2. 权限模型：角色 × 员工等级

企业里「能不能操作」和「能不能看」是两件事，混成一个等级一定会出问题：
部门主管（L3）需要能传文档、改密级，但不该能签发 API 密钥；
高管（L5）该能看所有文档，但不需要有删除权限。

所以拆成两个正交维度。

### 2.1 员工等级（数据权限，1~5）

| 等级 | 名称 | 可读文档密级 |
|---|---|---|
| L1 | 普通员工 | 公开 |
| L2 | 高级员工 / 组长 | 公开、内部 |
| L3 | 主管 | 公开、内部、部门 |
| L4 | 经理 / 总监 | 公开、内部、部门、管理 |
| L5 | 高管 / 负责人 | 全部，含机密 |

文档有 `min_level`（1~5，默认 1）。**判定发生在检索结果返回之前**：
SQL 取回候选块后逐条比对 `min_level <= 调用者等级`，不满足的直接丢弃。
这条过滤同时作用于词法候选和向量候选，不是只在前端隐藏。

下载原件、查看文档详情、读取版本历史都走同一判定。

### 2.2 角色（功能权限）

| 角色 | 定位 | 关键权限 |
|---|---|---|
| `owner` | 企业负责人 | 全部（`*`），含成员与密钥 |
| `admin` | 知识库管理员 | 文档增删改、密级、空间、FAQ、密钥、成员、审计、重建向量 |
| `manager` | 部门主管 | 文档增删改、密级、空间、FAQ、看审计、邀请成员 |
| `editor` | 内容编辑 | 上传/编辑文档、FAQ，不能删成员/发密钥/改密级 |
| `viewer` | 只读成员 | 只能检索与查看 |

权限点：`doc.read / doc.write / doc.delete / doc.level / space.* / faq.write /
key.read / key.write / member.read / member.write / member.invite / audit.read / stats.read / vector.rebuild`

**服务端逐条校验，前端隐藏只是减少误操作。** 越权返回 403 并写审计日志。

### 2.3 防提权规则

- 只有 `owner` 能授予 `owner`；
- 不能创建/修改**角色等级 ≥ 自己**的成员；
- 不能修改**员工等级高于自己**的成员；
- `admin` 不能创建 `owner`（实测返回 403）；
- 不能把自己降级/提权（要另一个负责人操作）；
- 不能把文档密级设得高于自己的员工等级（editor 改密级直接 403）；
- 企业必须至少保留一个 `owner`，删最后一个会被拒绝。

### 2.4 API 密钥也有等级

服务侧集成不该天然拥有全部数据权限。`api_keys.reader_level`（默认 5）限定该密钥能读到的最高密级：

```
POST /v1/admin/keys  { "name": "订单系统", "scopes": ["search","read"], "reader_level": 2 }
```

调用方还可以在请求体里再压低（`"level": 1`），但**抬不过密钥自身的等级** ——
取 `min(密钥等级, 请求等级)`，防止业务系统自己声明一个高等级来越权。

### 2.5 后台账号与会话

- 密码用 `scrypt(N=16384, r=8, p=1)` + 16 字节随机盐，库里只存哈希；
- 会话是 `admin_sessions` 里的随机 48 位十六进制 id，Cookie `HttpOnly; SameSite=Lax`，默认 12 小时；
- 登出 = 吊销该会话；重置密码 = 吊销该账号所有会话；
- 登录失败不区分「账号不存在」和「密码错误」，避免被用来枚举成员；
- 新成员默认生成 14 位初始密码，**只在创建时显示一次**，并标记 `must_change`。

## 3. 向量库

### 3.1 与原文同库，不再单独一个文件

早期版本是 `data/tenants/<id>/vectors.db`，现在改成主库里的两张表：

```sql
vectors(chunk_id PK, tenant_id, doc_id, space_id, dim, model, vec BLOB, updated_at)
vec_meta(key, value)   -- model / dim / ver
```

为什么合并：

1. **备份只有一份**：不用再记「拷三个文件还是六个文件」；
2. **不会对不上**：删文档时原文块和向量在同一个事务里，不存在「向量残留」；
3. **重建更快**：不用跨库复制。

写入用 `SAVEPOINT vec_write` 包住 —— 主库本身的入库流程已经有事务，嵌套事务会报错，`SAVEPOINT` 是唯一能安全嵌套的方式：

```js
db.exec('SAVEPOINT vec_write');
try { fn(db); db.exec('RELEASE vec_write'); }
catch (e) { db.exec('ROLLBACK TO vec_write'); db.exec('RELEASE vec_write'); throw e; }
```

代价是「换模型只重建向量」不再是通过删文件实现，而是走 `POST /v1/admin/reindex` 或 `scripts/embed.js --force`。
`vec_meta` 里记了 `model` 与 `ver`，进程内缓存按这两个值失效。

存储是 Float32 BLOB：本地 256 维 = 1KB/块，10 万块约 100MB。
检索走内存全量点积（首次访问把整个库的向量读成连续 `Float32Array`），
10 万块 × 256 维约 25M 次乘加，单次 20~40ms。超过 20 万块应换 ANN 索引，
只需替换 `src/vectors.js` 的 `search` 实现。

### 3.2 向量模型：默认本地，可切真实模型

默认 `hash-256-v2`：分词器的词（中文 bigram + 英文词，已过同义词归一）+ 单字 + 字符三元组，
用 FNV-1a 带符号哈希到 256 维，tf 取 `1+log(tf)`，最后 L2 归一。零依赖、离线、结果确定。

它的能力边界要说清楚：**能做字面近似（错别字、分词差异、部分重合），不能做真正的同义改写**。
「酒店」和「住宿」在哈希空间里不接近，这是特征哈希的固有限制，不是调参能解决的。

要真正的语义召回，配一个 embedding 接口即可（OpenAI 兼容）：

```json
{
  "embeddings": {
    "baseUrl": "https://api.openai.com/v1",
    "apiKey": "sk-...",
    "model": "text-embedding-3-small",
    "dim": 1536
  }
}
```

或环境变量 `KB_EMBED_BASE_URL` / `KB_EMBED_API_KEY` / `KB_EMBED_MODEL` / `KB_EMBED_DIM`。
接口约定：`POST {baseUrl}/embeddings` 入参 `{model, input:[...]}`，返回 `{data:[{embedding:[]}]}`。

配了远程模型后，入库不再同步写向量（远程接口是异步的，会拖慢入库），
需要跑一次批量补齐：

```bash
node scripts/embed.js            # 补齐缺失
node scripts/embed.js --force    # 全量重建（换模型后）
node scripts/embed.js --stats    # 只看状态，会标出模型不一致
```

### 3.3 混合打分

```
lexical = BM25 × (1+0.35·短语) × (1+0.20·章节 + 0.15·标题) × (1+0.12·邻近) × (0.75~1.20·硬词)
final   = 0.7 × (lexical / 最高 lexical) + 0.3 × cos        （权重可配）
```

两个防噪声设计：

- **余弦噪声门限**：`cos < 0.25` 直接当 0。弱相似度没有语义意义，
  但它足以在两条词法接近的候选之间随机改顺序 —— 这会实打实地降低准确率。
- **语义救援**：词法完全没命中、但 `cos ≥ 0.45` 的块，最多放 2 个进结果。
  这是「换个说法就搜不到」的唯一解，但门槛设得保守，避免引狼入室。

### 3.4 实测（`node scripts/eval-retrieval.js`）

14 篇文档 / 28 条标注问题（含 6 条「换词题」，与原文几乎没有相同 bigram）：

| 指标 | ① 纯 BM25 | ② + 短语/字段/邻近/硬词 | ③ ② + 向量（本地哈希） | ③ ② + 向量（语义模型*） |
|---|---|---|---|---|
| top-1 准确率 | 71.4% | 75.0% | 75.0% | **82.1%** |
| recall@3 | 85.7% | 85.7% | 85.7% | **96.4%** |
| MRR | 0.786 | 0.804 | 0.804 | **0.881** |
| 换词题 top-1 | 16.7% | 16.7% | 16.7% | **33.3%** |

\* 用 `scripts/mock-embed-server.js` 提供的规则向量器跑通链路（它不是模型，只是把同义说法映射到同一概念维），
用来证明「配置语义模型后这条链路确实生效」，不代表真实模型的水平。

**结论要直说**：本地哈希向量在这一版几乎不提升排序（75.0% vs 75.0%），它保证的是**不回退**。
向量层的价值要等接上真实 embedding 才会有 —— 上表第四列就是这个差值的量化。

评测跑在独立库 `data/eval/kb.db` 上，脚本启动时自己设 `KB_DB`，不会碰正式数据。

`http://127.0.0.1:7300/admin`

六个页签：概览（语料/向量/存储/缓存/最近操作）、文档与密级（逐篇改密级、下载原件、删除）、

## 5. `/v1` 接口的变更

| 变更 | 说明 |
|---|---|
| `POST /v1/search` 新增 `level` | 可降低读取等级，不能超过密钥的 `reader_level` |
| `POST /v1/search` 响应新增 `retrieval` | `{mode: hybrid\|lexical, vector_model, vector_candidates, ...}` |
| `POST /v1/search` 新增 `plain` / `vector` | `plain:true` 退化为纯词法（评测用）；`vector:false` 关掉向量路 |
| `POST /v1/ask` 新增 `level` | 同上；响应回显 `reader_level` |
| `GET /v1/documents`、`/v1/documents/{id}`、`/v1/documents/{id}/file` 新增 `level` | 按等级过滤/校验，`level=1` 只看公开，不传则按密钥等级 |
| `GET /v1/faqs` 新增 `level` | FAQ 里也可能写着不能全员可见的口径，列表同样按等级过滤 |
| `POST /v1/documents` / `POST /v1/uploads` / `POST /v1/faqs` 新增 `min_level` | 密级 1~5，会被密钥等级截断（取较小值） |
| 响应 `Hit` 新增 `min_level` / `uploader` / `file_id` / `parse_status` | 调用方能知道这条出自哪一级密文档 |
| `GET /v1/meta` 新增 `corpus.vectors` / `corpus.database` / `reader_level` | 能直接看到本企业库文件路径与向量规模 |
| `GET /v1/meta` 新增 `capabilities.instance`、`capabilities.isolation = single-instance-database` | 调用方能确认这是一套独立部署 |
| `GET /v1/admin/instance` / `PATCH` | 本实例概况与改名，取代旧的 `/admin/tenants/:id` |
| `GET /v1/admin/keys` / `POST` / `DELETE /:id` | 密钥不再挂在企业 ID 下 |
| `POST /v1/admin/reindex` | 不再需要企业 ID |
| `POST /v1/admin/tenants` | **已下线，返回 `410 gone`** |
| `GET /v1/admin/tenants` | 兼容保留，只回本实例一条；`GET /:id` 同 |

响应里的 `score` 语义变了：从「BM25 原始分」改为 **0~1 的融合分**
（`0.7×词法归一 + 0.3×余弦`）。排序行为不变，但如果你有基于绝对分值的阈值逻辑，需要重新校准。
`score_detail` 里仍然保留 `bm25` 原值便于排查。

### 5.1 密级必须「处处过滤」，不能只在检索里过滤

最容易出的漏子是：检索路径挡住了，但列表/详情/原件下载/FAQ 直答各漏一条。
本轮就踩了两个，都是靠断言抓出来的，记在这里避免回退：

| 漏洞 | 现象 | 修法 |
|---|---|---|
| 列表过滤把 `minLevel=1` 当成「不筛选」 | L1 密钥 `GET /v1/documents?level=1` 仍然返回 L4 文档（10 篇 vs 应为 7 篇） | `minLevel` 为 `null` 才表示不筛选；传数字一律加 `min_level <= ?`；后台 owner 改为传 `null`、能力上限另记 5 |
| FAQ 列表没做等级过滤 | L1 密钥 `GET /v1/faqs` 能读到 L4 的折扣底线问答，而 `/v1/ask` 却命中不了（口径不一致反而更危险） | `listFaqs` 支持 `minLevel`，接口层传 `effectiveLevel()`，后台按成员等级传 |

对应的回归断言（`scripts/smoke-test.js`）：

- 低等级密钥的文档列表不含机密文档
- 高等级密钥可按 `level` 压低列表范围
- 单篇读取也认 `level` 压低
- 低等级密钥的 FAQ 列表不含机密条目
- 低等级密钥不会命中机密 FAQ

### 5.2 密级是元数据，内容没变也要能改

同一个 `source_uri` 内容哈希一致时，入库走 `skipped` 提前返回——这本身是对的（幂等），
但会让「只想把某份文档从 L1 提到 L4」失效。现在的处理是：
**调用方显式给了 `min_level` 且与原值不同**，就在 skip 分支里顺手更新密级，
返回 `{status:'skipped', releveled:true, reason:'内容未变化，仅把密级从 L1 调整为 L4'}`。
不传 `min_level` 时沿用原值，避免一次同步就把机密文档降级成公开。

后台改密级走 `PATCH /admin/api/documents/:id`，与入库路径互不影响。

```bash
# 备份（不停服；WAL 模式下把三个文件一起拷）

  node scripts/embed.js --force

node cli.js tenant:list
node scripts/embed.js --stats
```

`GET /v1/admin/instance`（根密钥）会给出库文件绝对路径、字节数、语料规模、成员数、密钥数与空间列表 ——
排查「到底读的是哪个库」时看这个就行。

### 6.1 改动后必须跑的回归

```bash
node scripts/smoke-test.js        # 86 项断言：单库结构、密级、后台 RBAC、向量、上传解析
```

`smoke-test.js` 跑在独立目录 `.tmp-smoke/`（`KB_DB` + `KB_INSTANCE_ID=smoke`），

新增过滤入口时请一并加断言——本轮两个漏子都是靠这类断言发现的。

## 7. 已知限制

1. **向量检索是单进程内全量点积**，不是 ANN。20 万块以内够用，再大要换索引实现。
2. **本地哈希向量不做同义改写**（见 3.4 实测），语义能力取决于接入的 embedding 模型。
3. **远程 embedding 后入库不再同步写向量**，必须跑 `scripts/embed.js` 补齐，否则新文档只有词法索引。
   接口返回里能看出来：`retrieval.vector_candidates` 覆盖不到新块。
4. **角色是固定五种**，没有自定义角色/权限点编辑。企业要更细的划分需要改 `src/rbac.js` 的权限表。
5. **没有 SSO / 企业微信扫码登录**，只有邮箱密码。接 SSO 的话替换 `/admin/api/login` 的认证段即可。
6. **密级只有 5 档且是线性的**，没有「同部门可见」「项目组可见」这类横向隔离。
   需要按部门隔离时，给文档加 `allowed_roles` 再用密钥的 `roles` 收窄。
7. **新增企业要起一套服务**，没有「一键开企业」。这是刻意的取舍（见 1.3）；
   批量部署用容器或 `systemd` 模板，一企业一个 unit、一个端口、一个目录。
8. **列表接口单次最多 200 条**（`limit` 会被截断），密级过滤后翻页总数与页大小都由数据库算，
   不存在「先取 200 再过滤导致空页」的问题——但如果要做导出，需要自己按 `offset` 循环。
9. **后台账号没有登录失败锁定**，只有密码强度要求（≥8 位、含字母与数字）与 12 小时会话。
   对外暴露 `/admin` 前建议在反向代理层加 IP 白名单或失败次数限流。
10. **单进程单写**：一个实例同时只有一个写入者（SQLite 写锁），批量入库建议串行跑，
    多实例之间互不干扰 —— 这也是单实例部署顺带换来的好处。
